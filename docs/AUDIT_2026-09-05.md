# DMC5 DualSense 1.7.3 — portability and failure-path audit

Audit date: 2026-09-05. Source baseline:
`7a3dd8acbda482296d0db340e2d14502f92a687a`.

## Executive assessment

The accepted single-DualSense USB setup is not evidence of trouble-free
installation on every Windows PC. Normal installation and the tested controller
logic pass, but specific failure paths and a fallback dependency are real gaps.
Do not describe the entire C# package as requiring no additional runtime.
Do not describe hotplug or the current self-test as verified/reliable.

This audit adds tests and documentation only. It does not change the installed
mod, controller input/output implementation, Steam configuration, drivers,
published archives, release descriptions, or GitHub history. Nothing was
committed or published. The game was not launched during this audit. Test
Bridge processes ran in isolated folders without the real Steam API or audio.

## Confirmed high-priority findings

### A1. C# fallback has a hidden runtime dependency

Evidence: the archive's
`Dependencies/CSharpAPI/reframework/plugins/REFramework.NET.runtimeconfig.json`
requests `Microsoft.NETCore.App` 10.0.0. `REFramework.NET.dll` imports
`ijwhost.dll`, `VCRUNTIME140.dll` and `MSVCP140.dll`. The Bridge being published
self-contained does not supply a shared runtime to this separate in-game
C++/CLI module. The package has no standalone shared-runtime installation for
that module. The development PC already has Microsoft.NETCore.App 10.0.9.

A hostfxr configuration-resolution test succeeded with the PC's .NET directory
(`0x0`) and failed against the extracted mod directory (`0x80008096`, framework
missing). No system runtime was removed to obtain this result. A no-.NET clean
VM has NOT been tested; that remains the full end-to-end acceptance gate.

The lightweight binaries and bundled loader import Windows system libraries,
not MSVCP/VCRUNTIME or .NET. The additional managed dependency therefore does
not invalidate the recommended native package's runtime-independence claim.

Action: either declare and check .NET 10 x64 / VC runtime requirements for the
fallback, or redesign/bundle its in-game host properly. A larger self-contained
Bridge alone is not the fix. Verify on a fresh Windows image.

Supporting primary references:
[Microsoft C++/CLI deployment](https://learn.microsoft.com/en-us/dotnet/core/porting/cpp-cli),
[.NET host components](https://github.com/dotnet/runtime/blob/main/docs/design/features/host-components.md).

### A2. Incomplete update removes the previous working installation

Both installers invoke the existing uninstaller before checking all incoming
required files (`Native/Package/Install.ps1:255`, `Package/Install.ps1:253`).
Reproduction: install the release into a mock game, remove the incoming Bridge
EXE from an audit copy, run the update. It reports the missing file, but the
previous installed Bridge is already gone. An antivirus quarantine or incomplete
extraction can produce this situation without the user editing anything.

Action: validate/stage the entire incoming package before touching the old
installation, and retain a transaction snapshot through upgrade completion.

### A3. Installer accepts corrupt payloads; late rollback blocks retry

Two separately reproduced failures in both packages:

- Replace the audit copy's Bridge EXE with plain text while leaving
  `release-manifest.json` unchanged. Installation reports success. Installed
  hashes describe whatever was copied; they do not validate it against the
  release's expected hashes.
- Invalidate one target entry in the mock PAK before installation. The
  installer rejects the conflict and rolls back executable files. After
  restoring the mock PAK, retry still fails because rollback left `backup`
  and, for native, `Haptics` directories without an install manifest.

Action: validate required payload hashes before mutation; safely remove only
transaction-owned empty directories on rollback; retain enough recovery state
for a retry. Do not solve this by deleting arbitrary user mod directories.

### A4. Hotplug output recovery is not implemented reliably

`Native/Bridge/platform.cpp:168` and `Bridge/SteamInputOutputDevice.cs:129`
return success immediately while the cached handle is nonzero. They do not
re-enumerate an established controller to notice it disappearing/reappearing.

The native mock presents handle 101, disconnects it, then presents handle 202:

```text
PASS initial controller 101 selected
After disconnect: connected=1 writeReportedSuccess=1 lastTarget=101
After reconnect with handle 202: writeReportedSuccess=1 lastTarget=101 enumerationCalls=1
FAIL reconnect tracks replacement handle
```

Output APIs return void; the success counter counts calls, not hardware
acknowledgements. Cached `controllerReady=true` therefore cannot prove the
device still receives effects. The C# implementation has the same cached-handle
condition; the fake-API lifecycle test here executed the native implementation.

Native audio has a related reviewed risk: `render_loop` does not clear
`is_started` when the endpoint is invalidated or the render loop exits, while
`start()` immediately succeeds if that flag remains set. Full reconnect needs
both Steam-output and audio recovery, not a remapping-table change.

Important: this proves an OUTPUT-handle defect. It does not establish why the
game's Steam-owned INPUT sometimes disappears after USB reconnection. That
requires a separate real Steam/input test. Do not reintroduce virtual input,
direct HID ownership, or unrelated input workarounds on the basis of this mock.
Hotplug was previously deliberately deferred; this audit does not undo that
decision or ship another attempted hotplug patch.

## Other confirmed findings and reviewed risks

### A5. Self-test can report success without running

Both release executables return exit code 0 when the global Bridge singleton
already exists. An isolated `--self-test-all` run with only the named mutex
present reproduced that false success in both packages. No controller or
audio test happened. Separately, the full test checks controller readiness at
startup without waiting for Steam enumeration; installed September 3 logs show
`controller=0,haptics=1,samples=12`, explaining the reported startup error.

Action: distinct "already running/test not performed" result; bounded readiness
wait; useful connection/audio details surfaced to the user. Never call a
successful API submission a physical test pass.

### A6. C# configuration handling is not equivalent to C++

Malformed JSON crashes the released managed Bridge before its normal logging
starts (isolated test exit `-532462766`, unhandled `JsonException`). Native falls
back to defaults silently. Also the managed plugin sends to fixed UDP port
27105 (`Plugin/DMC5DualSense.cs:17,69`), while its Bridge reads configurable
`Port`. Changing that field breaks managed telemetry. Native reads a port on
both sides, but uses different parsing rules in plugin and Bridge.

Action: a shared validated configuration contract; explicit diagnostics and
safe bounded ranges; consistent UDP port resolution. Avoid silently re-enabling
effects the user disabled when the rest of the config is malformed.

### A7. Multiple controllers can route feedback inconsistently

Code review, not a two-device hardware reproduction: Steam output chooses the
first PS5 handle; audio independently chooses its highest-scored endpoint;
the fallback trigger snapshot reads the first XInput device. There is no
shared selected-device identity tying all three together. With two DualSense
controllers (or another XInput pad), effects need not reach the playing pad.

Action: explicit device association/selection, or an honest one-controller
limitation with a diagnostic warning. No support claim for multi-controller
routing until tested with two physical devices.

### A8. Third-party loaders, audio changes and version drift

- Existing REFramework recognition uses PE architecture plus a marker string,
  not a verified loaded API version. Native requires API 1.10; fallback requires
  1.15. Preserving an older loader can leave UI present but feedback absent.
  The existing preservation test flips a byte of the bundled DLL as a fixture;
  it does not prove compatibility with every actual REFramework version.
- Unknown-loader replacement preserves/restores the file, but backup is not
  runtime co-loading. Other mods depending on that loader may be unavailable
  while it is replaced. Keep the confirmation; never silently erase it.
- Other mods can invalidate the same PAK entries or replace the same UI assets.
  The installer rejects an already-invalidated target (reproduced above).
  Steam verification restores original PAK entries: a repair/reinstall is
  then needed for the loose GUI changes. The repair path passed in mocks.
- Endpoint selection permits recognized devices with fewer than four channels.
  Successful audio initialization alone does not prove rear haptic channels
  are being driven. Disabled endpoints, stereo configuration, spatial audio,
  exclusive users and USB audio reinitialization need device-level coverage.
- The default audible-endpoint setting temporarily unmutes/sets its volume.
  Orderly cleanup restores an unchanged managed volume; process termination or
  another application changing it is a separate recovery scenario.
- SteamInput006 uses ABI method indices and the plugin relies on game reflection
  contracts. New Steam/game/framework versions need a capability failure path,
  not a claim that all future versions are automatically supported.

These reviewed risks are not asserted to have all occurred on users' PCs.

## Tests passed and limitations

Passed in this audit:

- managed deterministic logic suite and a fresh native build/test suite;
  remap-aware trigger logic, motor timeout independence, bounded haptic mixing,
  and ordinary-rumble/advanced-haptics arbitration;
- both exact public ZIPs: no nested archives; installed file hashes verified
  (33 native / 35 managed owned files in the clean fixtures);
- six existing install/uninstall/loader scenarios per package, including
  decline-without-change and restoration of replaced loader bytes;
- edited configuration preserved byte-for-byte during reinstall;
- Windows PowerShell 5.1 installation with spaces, brackets and Chinese
  characters in the mock game path;
- C++ → C# → C++ installation sequence with one implementation active and no
  installed-manifest hash mismatches; original mock PAK restored on uninstall;
- both release Bridges report missing Steam API rather than claiming connected;
- both isolated sessions exit when their own parent process ends and remove
  their ready files, with no actual controller/audio/Steam API;
- repair after mock Steam PAK verification, followed by exact uninstallation;
- installed native binaries and six UI assets match public release contents.

Not performed: a fresh Windows VM without development dependencies, an actual
other PC, Bluetooth/Edge/ZCT2 hardware, simultaneous controllers, physical USB
disconnect/reconnect, sleep/resume, tactile intensity comparison, game visual
checks at other resolutions/languages, real mod-manager interoperability or
Windows security-product quarantine scenarios. No antivirus was disabled and
no user was instructed to whitelist arbitrary DLLs.

## Maintenance and MacBook handoff

Current GitHub CI builds the managed Bridge/Launcher/UI tool and runs managed
logic tests. It does not build native code or execute packaged install/runtime
failure-path tests. Latest inspected baseline run passed:
https://github.com/niczapol/dmc5-dualsense-mod/actions/runs/33631619883

Recommended next gates, before declaring cross-PC readiness:

1. Fix installer transactions/hash validation with A2/A3 tests turning green.
2. Correct fallback dependency handling and test on a clean Windows image.
3. Make diagnostics truthful (A5) and configuration consistent (A6).
4. Add native plus packaged-release tests to Windows CI. The new tests intentionally
   fail against 1.7.3; do not hide/skip their findings to make CI green.
5. Treat hotplug as a separate state-machine/input-and-output acceptance task.
   At minimum validate device absent at launch, late connection, unplug idle,
   unplug during feedback, reconnect, and repeated cycles on real USB hardware.
6. Add a support bundle containing versions, relevant config, selected-device
   identity, input/output/audio state and recent logs. Redact serial numbers,
   user paths and other identifiers before public posting.

The reproducible audit tests are in `Tests/Portability/`. Their README describes
the safe fixtures and commands. They can be edited on a Mac, but Windows-specific
execution still needs a Windows host/CI. No new Windows machine or cloud job

## Documentation corrections to carry forward

The existing handoff has stale bullets naming `app.GameManager.KeyAssign` as
the active remap source and describing XInput-gated USB recovery. For this
release, use the character SaveDataManager KeyAssign mapping in the current
plugin source; hotplug is deferred and not proven. `version.json` also retains
the old release title "Nero Remap-Aware Resistance" despite Version 1.7.3.
The installed rc1 BUILD_INFO label and the public README's fallback
"neither requires additional software" claim should be corrected in a
controlled follow-up. This audit report supersedes those specific claims;
it does not silently rewrite published documentation.
